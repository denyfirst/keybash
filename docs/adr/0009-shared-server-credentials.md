# 0009 — Shared credentials: people connect with a server's key without seeing it

Date: 2026-11-23. Status: accepted direction, under the maintainer's standing
delegation for self-hosted features; built in phases, each its own pull
request. This is phase D of ADR 0005.

## Context

Today every connection uses a credential its owner holds. A person who reaches
a server through Keybash therefore brings their own key or password. That
password can be read back: the vault shows a secret after fresh proof. A key
they imported has been on their own computer. Either way, the person can reach
the server without Keybash. Taking someone off a server's access list then does
not take away what they know: an administrator also has to change the server's
password or remove their key there, and must not forget one.

A privileged access manager exists to close that gap. An administrator should
be able to let people onto a server with a credential that stays inside
Keybash. They connect, but they never see it, so removing them from the list is
the whole revocation.

Keybash already has the pieces this needs:
- a key generated here, whose private half never leaves (`Generated`);
- per-server access lists that end sessions at once when someone is removed;
- records sealed under the instance key;
- fresh proof for sensitive changes.

## Decision

### What a shared credential is

- A server may have **one** shared credential, set by an administrator. It
  belongs to the server, not to a person. It is stored in its own sealed
  record, bound to the server's ID.
- **SSH:** a key **generated by Keybash** (Ed25519), never imported. Its
  private half is never shown or exported, to anyone, administrators
  included; backups carry it only inside the sealed database. It leaves only
  as signatures, as a generated personal key does today. Keybash shows the
  public half as a line to add to the account's `authorized_keys`, with
  `restrict,pty` in front. So even a key used through a compromised gateway
  cannot forward ports or agents through the server.
- **SSH password or RDP password:** typed once by the administrator, who
  necessarily knows it, and never shown again, to anyone. The page says so,
  and says to change the password on the server when that administrator
  leaves.
- The record holds the account's user name, the kind, a key's public half,
  who set it and when, and whether it has worked once (as `Used` does for
  personal keys).

### Who does what

- **Administrators** set, replace and remove a server's shared credential on
  the Servers page. Each change needs fresh proof, like adding a server.
- **Auditors** see whether a server has one: its kind, user name, public key,
  who set it, and when. Nothing else.
- **People on the server's access list**, administrators among them, connect
  with it. They see nothing of it but its user name.

### How people use it

- A server with a shared credential appears on the Connections page of
  everyone on its access list as a ready card, marked "Shared by your
  administrator". It needs no setup. Personal connections to the same server
  still work.
- Opening it goes through the same lease as any connection. The lease is
  bound to the person, their session, the server's approval, and the shared
  credential's record revision. At redeem time Keybash checks again:
  - the person is still on the access list;
  - the server is still the same;
  - the credential has not been replaced or removed since the grant.
  Anything else is refused, and nothing is dialled.
- The worker receives the credential exactly as it does a personal one today.
  Nothing new crosses the sandbox, and the browser never receives it.

### Replacing and removing it

- **Replacing an SSH key takes two steps,** so the server is never left
  without a working key:
  1. A new key is generated next to the current one, and the page shows its
     line to add on the server.
  2. When the administrator confirms, the new key becomes the one used, and
     the old one is destroyed. Its line can then come off the server.
  Until then, the current key keeps working.
- **Replacing a password** takes effect at once: the administrator changes it
  on the server first, then here.
- **Removing it** ends every open session that used it, at once, as removing
  a person from the list does.
- Replacing it does not end open sessions: the key never left Keybash, so
  nobody gained anything to take away.
- **Removing a person from the access list is their whole revocation.**
  Their open sessions end at once, as today, and they never held the
  credential.
- Removing the server removes its shared credential with it.

### What does not change

- "Start over" and a password reset leave shared credentials alone, because
  they belong to the server.
- Backups carry them inside the sealed database, like every record, and a
  restore needs the instance key as before.
- No API answer, log line, journal entry or error message carries the secret.
  Responses carry only the summary above, and `Format` redacts the record, as
  it does `Credential`.

## Tests each phase must bring

Following `ENGINEERING.md`, with sabotage both ways:
- refusal for a person not on the list, a removed person, a replaced or removed
  credential between grant and redeem, and a user or auditor trying to set,
  replace or remove one;
- fresh proof required for each change;
- the secret absent from every response, the browser and the journal (a
  marker search, as PR 109 did);
- malformed and oversized records refused on read;
- a key's line shown with `restrict,pty`;
- the two-step replacement: the old key works until the confirmation and is
  destroyed after it;
- removal ending sessions, while a replacement does not.

## Phases

1. **Store and API.** The sealed record; set, replace (two-step for keys) and
   remove, with fresh proof; summaries for administrators and auditors; and
   the access-list and revision checks at grant and redeem.
2. **Servers page.** The administrator's side: set, the key's line with a copy
   button, replace, confirm and remove; the auditor's read-only view.
3. **Connections page.** The shared card for people on the list, and opening it
   from SSH and RDP.
4. **Live check** on the test VM, against the Linux test account and the Windows
   test server, with the marker search for the secret.

## Progress

- **Phase 1** (store and API):
  - the sealed record (`internal/identity/shared.go`, namespace
    `shared-credentials-v1`, carried by backups);
  - the administrator's actions under `/api/servers/{id}/`: `shared` (set, or
    remove with DELETE), `shared-password`, `shared-next` (make, or drop with
    DELETE), `shared-switch` with the fingerprint seen;
  - the summary on the Servers list;
  - `GET /api/shared` and `POST /api/remote/open-shared` for people on the list;
  - the checks at grant and redeem.
  The page comes in phases 2 and 3; until then nothing on the website uses it.
- **Phase 2** (Servers page):
  - A server's row says whether it shares a key or a password, and for which
    user. A key's row also says whether it is in use, or whether a new key is
    waiting.
  - An administrator's "Share a key" (SSH) or "Share a password" (RDP) opens a
    sheet that shares one. For SSH they may choose a password instead of a key.
  - Afterwards the sheet shows a key's command for the server, with its own
    Copy. It makes a new key, shows that key's command too, and then uses it
    or keeps the current one. A password is changed in the same sheet.
  - "Stop sharing" asks first.
  - A typed password is emptied from the page as soon as it is sent.
  - Auditors see the row's line and no actions.
- **Phase 3** (Connections page):
  - Everyone on a server's list sees a card for its shared credential,
    marked "Shared by your administrator", before their own connections. It
    shows the account's user name and nothing else, and needs no setup.
  - The card says "Ready", "Server changed" (a desktop shows another
    certificate than its pin, so nothing is sent until an administrator
    checks it) or "Unavailable". Only a ready card offers to connect.
  - Connect opens `/remote/shared/ssh/{server}` or `/remote/shared/rdp/{server}`
    in its own tab. The page is served only to someone who could open the
    credential, and it opens it by the server's ID through `open-shared`.
  - The page refuses a shared row with any field it does not show.

## Limits

- A shared password was typed by a person, so they know it. Only a generated
  SSH key is unknown to everyone. Rotating a password on Windows remains the
  administrator's job, and the page says so.
- A compromised gateway can use any credential it holds, shared or personal.
  The kernel boundary (ADR 0005, A) still limits where it can reach, and
  `restrict,pty` limits what a key can do there.
- The record of who connected where and when, and the command log, are the next
  phase, not this one.
